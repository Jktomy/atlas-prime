# Odyssey Hermes-Native Architecture Contract

## Authority and scope

This contract canonizes the settled portion of **The Odyssey — Hermes-Native
Atlas Architecture Preview R01**, accepted on Mission `#364`.

- Issue `#359` remains the sole living Odyssey Quest parent.
- Mission `#358` remains preserved architecture and admission evidence.
- Mission `#364` is the current accepted reconciliation and roadmap carrier.
- The canonical Campaign and gate remain `OD-C02 — Preserve the Old Flame` and
  `OD-C02-PREVIEW`.

This is source architecture, not implementation proof. It grants no software
installation, runtime, hardware, storage, backup, restore, account, credential,
protected-data, READY, MERGE, or cutover authority.

## Hermes-native-first rule

Atlas uses native Hermes capabilities before building a custom replacement for
the same responsibility. The initial target direction is:

```text
Hermes Agent
├── persistent profile identities for approved Cognitive Shadows
├── native sessions and compact lived continuity
├── native bounded delegation for temporary Sub-Shadows
├── Hermes Desktop as the primary conversational surface
├── Hermes Kanban as the future Mission Board target
└── native backup/export/recovery tested before custom recovery tooling

VS Code + Hermes integration
└── primary engineering, editing, testing, and construction surface
```

A custom service is admitted only after a Mission proves a material capability,
security, recovery, or usability gap that native Hermes cannot satisfy.

Hermes profile names, models, sessions, tools, and delegation never create
protected, infrastructure, canonical, READY, or permanence authority.

## Knowledge realms

### Protected private realm

```text
approved protected source
→ Emberdark validation, classification, authorization, quarantine, and receipt
→ Coppermind
→ Harmony
```

- **Coppermind** is the protected private knowledge domain.
- **Emberdark** owns governed crossing, admission, classification, quarantine,
  replay protection, workflow identity, and receipts.
- **Harmony** is the sole protected-to-shared sanitization and publication
  boundary.
- Uncertain sanitization remains private.
- Originals remain distinct from every extraction, record, index, summary, or
  publication.

OpenViking receives no Coppermind credential, mount, private network route,
unrestricted protected API, or authority to request protected facts from
Harmony.

### Sanitized shared realm

```text
Harmony sanitized publication
→ Obsidian
↕ OpenViking
→ Hermes retrieval and shared reasoning
```

- **Obsidian** is the durable sanitized shared hive mind.
- **OpenViking** is its autonomous curator, semantic adapter, and retrieval
  layer.
- OpenViking may create, update, rename, merge, split, reorganize, rewrite,
  archive, or delete sanitized shared notes.
- OpenViking indexes are derived and rebuildable; Obsidian content is durable.
- Recovery uses bounded snapshots and backups rather than a Git transaction for
  every note edit.
- Obsidian and OpenViking never become Prime, a protected-original vault, or the
  Mission Board.

## Stable infrastructure roles

The current target roles are:

```text
Prometheus
├── Proxmox foundation
├── 96 GB target RAM
├── 3 × verified 1 TB NVMe, proposed ZFS RAIDZ1
├── protected/shared realm VM — 72 GB target
├── Plex LXC — 8 GB maximum
├── protected Proxmox reserve — 8 GB
└── flexible capacity — 8 GB

Apollo
├── always-on Windows node
├── Hermes Agent and approved persistent profiles
├── Hermes Desktop
├── future Hermes Kanban target
├── VS Code + Hermes integration
└── selected persistent Helios processing

Forge
├── durable storage backbone
├── Protected Original Vault storage where separately approved
├── Anvil durable media/archive
├── Hammer transient landing and handoff
├── approved backup destination
├── Jellyfin continuity
└── Audiobookshelf continuity

Notum
└── independent minimal watchtower able to observe Prometheus failure
```

All capacities and placements are planning targets subject to exact inventory,
compatibility, thermal, stability, isolation, backup, restore, degraded-mode,
and rollback proof. No ballooning, overcommit, guest creation, disk formatting,
service migration, or deployment is authorized by this source.

The independent-recovery-copy requirement remains active. Forge may be an
approved destination, but the accepted working proposal to rely on Forge as the
sole durable destination is explicitly deferred and is not canonized here.

## Current authority surfaces

Until a separately proven atomic cutover:


No dual-write Mission-authority period is accepted. History reconstruction,
backup, restore, conflict behavior, parity, rollback, and exact readback must be
proven before any Mission Board transfer. Prime/GitHub retirement requires a new
explicit Preview and permanence transaction.

## Explicit deferrals

This contract deliberately does **not** settle or activate:

- the Shardblade naming collision; current Prime machine-permanence meaning remains unchanged;
- Mission Board cutover to Hermes Kanban;
- Prime or GitHub retirement;
- unresolved Kandra, Sazed, Worldhopper, Silverlight, Five Ideals, Edicts,
  Mistborn, Nightblood, Dawnshard, Seon, or other ontology;
- the sole-Forge recovery exception;
- software, model, database, or operating-system versions;
- exact runtime configuration, ports, credentials, network values, storage
  commands, database schemas, or deployment manifests;
- any claim that hardware, services, backups, restores, profiles, or connectors
  are installed or proven.

## Proof and rollback

Every implementation area remains separately Mission-bound with exact source or
runtime identity, protected boundary, tests, negative cases, recovery,
independent readback, and rollback. Before this source merges, rollback is
closing its exact PR. After merge, rollback is one reviewed revert or
repair-forward PR. History rewrite is forbidden.
