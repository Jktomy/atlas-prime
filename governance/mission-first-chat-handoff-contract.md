# Mission-First Chat Handoff Contract

## Purpose

Substantive Atlas work must not remain trapped in one chat. Chat is the discussion,
clarification, Preview, and authorization surface. The Mission Board is the required
public-clean operational coordination and restart surface for substantive work.
Merged Prime remains canonical doctrine and completed durable truth.

## Admission rule

Before substantive execution begins, the worker must create or resolve exactly one
Mission Board Mission and bind the exact attempt. The Mission must exist before any
of the following occurs:

- consequential Preview storage or later Build/Execute work;
- source mutation, branch construction, pull-request construction, validation,
  review reconciliation, READY, or permanence preparation;
- delegation or assignment to Codex, Athena, another Worldhopper, or a future
  session;
- multi-step sequencing, dependency management, deferral, blocking, or work that
  must survive the current conversation;
- Sunset, recovery, migration, infrastructure, continuity, protected-boundary, or
  runtime work.

A direct Jayson authorization may create and bind the Mission as the first performed
step of the same bounded transaction. Mission capture does not itself grant Build,
Execute, protected access, READY, or permanence authority.

## Exempt conversation

Do not manufacture a Mission for ordinary conversation, quick factual answers,
writing or rewriting, read-only orientation that creates no continuing work, or a
nonconsequential one-shot task fully completed in the same response with no blocker,
dependency, delegation, durable mutation, or follow-up obligation.

When uncertainty exists, preserve the user's semantic objective and ask whether the
work has an operational future. If it does, bind a Mission before substantive work.

## Public-clean transfer

Never copy an entire chat into the Mission Board. Transfer only the sanitized
operational substance required for discovery and restart:

- objective, owner, lane, route, scope, decisions, and approvals;
- Project, Operation, Quest, Campaign, Mission, and Gate relationships;
- exact transaction, base, branch, pull-request, head, checks, review, and receipt
  identities when they exist;
- blockers, dependencies, current position, next safe action, rollback, and restart
  instructions;
- bounded `protected://` pointers without protected values.

Secrets, credentials, private network or runtime data, PHI, raw financial or legal
records, unrestricted logs, and private exports remain outside Prime and the Mission
Board.

## Chat-to-Mission workflow

```text
substantive objective identified in chat
→ search for an existing exact Mission and attempt
→ create and bind one public-clean Mission when none exists
→ store the restart-safe Preview when required
→ receive the separately required Build or Execute authorization
→ perform bounded work and append verified progress to the same Mission
→ preserve blockers as BLOCKED_RESUMABLE
→ resume the same attempt from any authorized worker or session
→ close only after applicable completion proof and archival disposition
```

Duplicate Missions, branches, pull requests, or attempts are prohibited merely
because a chat, connector, or worker becomes unavailable.

## Blocked and interrupted work

A substantive transaction may not end only as chat text when it becomes blocked,
deferred, or interrupted. Before stopping, create or update the same Mission with:

- the exact attempt identity;
- truthful state and canonical-source posture;
- completed and unperformed actions;
- blocker and evidence references;
- restart instructions and the next safe action.

If the Mission Board itself is unavailable, preserve a public-clean export and stop
`BLOCKED_RESUMABLE`; bind it to the exact Mission when authenticated Issue access
returns. Do not create a replacement attempt.

## Sunset handoff

`Sunset this chat` remains Preview-first. Once an exact Sunset Preview is approved,
the transaction must have one `mission/sunset` identity before candidate
construction. If approval-carrier construction, repository access, publication,
validation, or permanence is blocked, the same Mission records `BLOCKED_RESUMABLE`
and preserves:

- Preview digest and approval mode;
- approved canonical base;
- formal carrier state;
- candidate, branch, and pull-request state;
- exact blocker and restart route.

A Mission handoff does not fabricate a formal lifecycle carrier or authorize manual
reconstruction of lifecycle bytes. Only merged canonical-main readback may claim
`SUNSET COMPLETE`.

## Worldhopper boundary

Assignment makes work discoverable to an authorized Worldhopper but grants no new
capability. Every worker must fresh-read current Prime, the complete Mission history,
current canonical source, dependencies, and exact live candidate state before action.
The worker resumes the same attempt, appends public-clean evidence to the same
Mission, and remains subject to Aegis, Noctua, Ares, Strikeforce, protected-data,
rollback, READY, and permanence gates.

## Acceptance

The doctrine is satisfied only when:

1. substantive work is Mission-bound before substantive execution;
2. chat-only approval cannot become a durable blocked transaction without a Mission
   handoff;
3. delegated workers can recover the same public-clean attempt without the original
   chat;
4. ordinary conversation remains exempt;
5. protected information never crosses into the Mission Board;
6. no Mission state or assignment is mistaken for canonical source, protected
   authority, runtime proof, READY, or permanence.
